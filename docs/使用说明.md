# 3DWET 使用说明

求解器是原生程序 `getm_cartesian`（Windows 上是 `3DWET/bin/getm_cartesian.exe`）。Python 只负责界面、启动和读结果，不另算一套水动力。

Windows：先运行 `setup_studio.cmd`，再双击 `launch_web.cmd`（浏览器）或 `launch_desktop.cmd`（桌面窗口）。仓库里的 `3DWET/bin/getm_cartesian.exe`（12202146 字节）带 OpenMP，仍然只依赖 Windows 自带的 `KERNEL32`、`msvcrt`、`SHELL32`。退出前会放开 OpenMP 线程池。旁边的 `getm_cartesian_serial.exe`（11738705 字节）是上一版静态串行程序，多核启动失败时用它。`bin/runtime` 里的 DLL 仍保留，供界面检查安装是否完整。不要删 `getm_cartesian_parallel.exe` 和 `bin/mpi/`。

Linux：在仓库里执行 `python3 3DWET/app/launcher.py --web --no-open`，浏览器打开它打印的地址。本机若还没有 Linux 可执行文件，用 `bash scripts/build_linux_solver.sh` 生成，不要把 `build-linux/`、`install-linux/` 或二进制提交进仓库。

## 跑滇池

案例在 `GETM-FABM-WET/3DWET/case/Lake Dianchi/`。网格是笛卡尔等距（`grid_type=1`，500 m，41×67，约 1150 个水格，10 层，步长 15 秒）。步长 60 秒会触到浅水河格的 CFL 限制，不能拿来和 EFDC 的 60 秒步长硬比。

求解只用笛卡尔、球面等距或正交曲线网格。界面里的三角网格选项、三角网按钮和“三角网”菜单都已去掉。食物网里的“三角闭环”指三条营养路径，仍然保留。

在「运行控制」里先做运行前体检，再开始。进度来自日志里的 `n=`。Patankar 在状态量接近 0 时会把分母托在 `1e-12`，重复警告只留前几条，避免进度停在某个百分比、日志被刷满。

## 使用核数

运行控制里的「使用核数」没有上限。第一次在一台机器上打开案例时，程序会读逻辑核、物理核、插槽和 NUMA（Linux 上能读到的话），以及有没有 `mpiexec` 或 `srun`。然后它用大约 300 步试几种 OpenMP 线程数，按积分速度（日志里相邻的 `n=`）选最快的，记在这台机器的 `~/.3dwet/core_calibration.json`。键是机器指纹、网格、水格数和求解器大小。换了机器、网格或程序会重测。

方式可以改成自动、OpenMP 线程、MPI 进程，或 MPI × OpenMP。自动用测定结果；滇池这种大约 1150 个水格的小湖，在测定完成前先按网格估一个不超过 4 的线程数，不会把 32 核或更多核全部占上。改数字就变成手动。选中的核数、实际 MPI 进程数、OpenMP 线程数会显示在运行监控里。多核启动失败，或者 90 秒还没有 `n=`，就改回 1 个线程并标明已回退串行。显式 MPI 如果还没开始步进就失败，同样改回串行。

`OMP_NUM_THREADS` 同时约束水动力里打开了 OpenMP 的循环，以及示踪物水平平流。平流用的是 `omp_get_max_threads()`，不再按机器核数自行占满。

## 运行监控

运行页上方的「运行监控」显示选用核数和方式、实际 MPI 进程数、OpenMP 线程数、步/秒、模拟天/墙钟小时、预计剩余时间、CPU，以及每个进程最近的输出。回退串行时会写明。进程退出后 CPU 和 OpenMP 线程数保留最后一次读到的值，不再变成「—」。约 90 秒没有新步进，或日志里出现致命错误时，这一栏会高亮。

## 集群上用 MPI

GETM 的区域分解已经在源码里，编译时加上 `-DGETM_USE_PARALLEL=ON`。可执行文件名会带 `_parallel`。水平晕区宽度是 `HALO=2`，每个子域的内点至少要盖住这个宽度，分得太碎时求解器会在启动时停下。FABM 热启动不支持 MPI，要冷启动。

在登录节点上先按 `scripts/build_linux_solver.sh` 装好 FABM，再另开一个并行构建目录（不要覆盖已经编好的 OpenMP 程序）。MPI 编译器按集群模块来：

```bash
cmake -S 3DWET/src/getm/src -B build-linux-mpi/getm \
  -DGETM_USE_PARALLEL=ON -DGETM_USE_FABM=ON -DGETM_COORDINATE_TYPE=Cartesian \
  -DFABM_PREFIX=3DWET/install-linux/fabm \
  -DCMAKE_Fortran_FLAGS="-O2 -fopenmp -DGETM_OMP -ffree-line-length-none"
cmake --build build-linux-mpi/getm --target getm_exe
```

作业脚本里：

```bash
# 纯 MPI。界面里方式选「MPI 进程」，核数填总进程数。
srun -n "$N" ./getm_cartesian_parallel

# MPI × OpenMP。方式选「MPI × OpenMP」。
export OMP_NUM_THREADS="$M"
srun -n "$N" --cpus-per-task="$M" ./getm_cartesian_parallel
```

本机没有 `srun` 时，界面会用找到的 `mpiexec -n N`。多节点、`srun` 和 Linux 的 `GETM_USE_PARALLEL` 构建在这台验证虚拟机上没有跑过。Windows 自带的 `getm_cartesian_parallel.exe` 是更早的程序，自动模式不会选它；只有手动选 MPI 才会启动，结果没有和这一轮的 OpenMP 程序对过。

## 看结果

水位和深度平均流速在二维结果里。三维流速是 `uu`/`vv`。信息栏给出表层均值、底层均值和两者之差。原生三维文件里 `k=0`（sigma 最底的填充层）不是湖底，湖底是下一个有限层，水面是最后一层。

每天必写的关键量在 `output.nc`：水温、深度、层厚、水位、溶解氧。溶解氧的场名是 `abiotic_water_sO2W`（下划线）。氨氮、硝氮、磷酸盐、叶绿素、蓝藻和其他水质状态量按周放在 `ext_wq.nc`，点开变量才读，界面会缓存最近几帧。周文件在求解器初始化时创建。默认只写各模块的状态量，再加三个藻类的 `oChla` 和合计 `wet_chla_calculator_result`。反应速率、限制因子这类诊断量不在默认名单里；需要时在 `ext_wq` 里加回 `source: fabm/<实例名>/*` 且 `output_level: 8`。不能写 `abiotic_water/*`，那个类别是空的，文件不会创建。模拟不满 7 天时文件里还没有周记录。求解器写出的是未压缩 NetCDF；界面默认在跑完后用 deflate 压缩 `ext_wq.nc`（与 `output.nc` 同一开关），变量名和数值不变。同一张滇池网格、一个时次：原先 794 个变量、58.9 MB；现在 122 个水质变量，未压缩 9.58 MB（9584972 字节），deflate 后 2.96 MB（2960557 字节）。这个大小用 1 天运行、写出间隔改成 1 天测得，和正式的 7 天间隔是同一条记录的体积。

原生 `*.3d.nc` 默认不再把全部 FABM 状态写进去（`save_fabm_native` 默认关闭，`getm.inp` 里不写这个开关）。同一天的滇池 WET 结果：旧文件约 64 MB、884 个变量；新文件约 756 KiB、24 个变量，仍有 `uu`，没有叶绿素。湿网格表层溶解氧均值约 9.61 g/m³（1150 个水格）。未掩膜的平均值会落到填充值附近，不要用。

## 速度（本机，2026-11-02，4 个逻辑核）

同一台机器、滇池案例、模拟 1 天（5760 步）。墙钟是进程从启动到退出。这一轮 `OMP_NUM_THREADS` 同时给水动力和示踪物平流。短跑测定（约 300 步，看 `n=` 之间的步速）也选出 2 个线程：1 线程 77.3 步/秒，2 线程 80.8 步/秒，4 线程 80.1 步/秒。

| 线程 | 墙钟 | FABM/WET | 示踪物平流 | 和 1 线程的最大差 |
| --- | --- | --- | --- | --- |
| 1 | 77.564 秒 | 72.02 秒 | 15.95 秒 | 参照 |
| 2 | 71.540 秒 | 65.72 秒 | 8.52 秒 | 水温、溶解氧、氨氮、蓝藻干重都是 0 |
| 4 | 72.072 秒 | 64.11 秒 | 5.21 秒 | 同上，0 |

平流还在变快，整段墙钟在 2 个线程进入平台期，4 个线程没有更快。这台虚拟机 `lscpu` 是 4 核、1 插槽，进程亲和 0–3。湿网格表层均值与上一轮相同：水温 13.967°C，溶解氧 9.60772 g/m³，氨氮 0.230715 g/m³，蓝藻干重 0.269848 gDW/m³（1150 个水格）。`LAKE_DIANCHI_WET.3d.nc` 仍是 773920 字节，`output.nc` 354420 字节。周文件在这次计时里把间隔改成 1 天，所以写出了一条记录，原始大小 9584972 字节。

同一份案例在 Wine 里跑新的 Windows 程序，三次都是退出码 0，日志过了 `clean_input` 和 `getm: Completed`，没有停在清理阶段。

| Wine 线程 | 墙钟 | FABM/WET | 示踪物平流 | 相对 Linux 1 线程的最大差 |
| --- | --- | --- | --- | --- |
| 1 | 184.889 秒 | 163.21 秒 | 76.92 秒 | 四个量都是 0 |
| 2 | 142.428 秒 | 123.31 秒 | 37.94 秒 | 0 |
| 4 | 149.998 秒 | 115.13 秒 | 31.54 秒 | 0 |

Wine 同样在 2 个线程进入平台期。四个量是水温、`abiotic_water_sO2W`、`abiotic_water_sNH4W`、`cyanobacteria_sDW`，各 11500 个湿层格点。

上一轮 68 秒是水动力 1 线程、平流按机器核数另开。现在核数选择对两边都生效，1 线程是真正的串行，所以比那 68 秒慢。测定完成前，1150 个水格先估 3 个线程；测定结果会盖过这个估计。32 核或更多核的机器上，这个估计仍然不超过 4，除非短跑证明更多线程更快。

关掉 FABM 时，1 个线程 4.76 秒、3 个线程 7.07 秒（更早的水动力对照）。开源 EFDC+ 只有温度时 4.69 秒（1 线程）和 5.48 秒（`-NT3`）。网格和步长不同，完整 WET 仍然比它慢。`split_factor` 默认没有改。

EFDC 源码和可执行文件留在本机 `/tmp`，仓库里没有 EFDC Explorer。另一台 12 线程电脑上的 `TIME.LOG`（约 3.5 秒）只作背景。

主路径用原生求解器。

## 还需要知道的限制

- Windows 程序现在带 OpenMP。退出前会调用 `omp_pause_resource_all`，避免静态 libgomp 在清理阶段一直不返回。若多核进程启动失败或长时间没有步进，界面改用旁边的 `getm_cartesian_serial.exe`（1 个线程）。`OMP_NUM_THREADS` 对 Windows 和 Linux 都生效。
- 上述 Wine 1 天算例与 Linux 新程序写出同一大小的结果：`LAKE_DIANCHI_WET.3d.nc` 为 773920 字节、24 个变量（有 `uu`），`output.nc` 为 354420 字节，溶解氧场名 `abiotic_water_sO2W`，湿网格表层均值 9.6077 g/m³（1150 个水格）。
- `1e-12` 下限会在导数很小时把状态托住。旧算法一打印 Error 就被界面杀掉，所以没有一条“不改算法也能跑完”的对照。
- 每周 `ext_wq.nc` 默认是状态量加叶绿素，不是 `fabm/<实例名>/*` 的全部诊断。旧的 `abiotic_water/*` 选不到变量，日志会写该类别没有匹配到请求的输出级别，文件不会创建。不满 7 天的运行可以有这个文件，但时间轴上还没有周记录。Flexout 本身不写 deflate；勾选结果压缩（默认勾选）后，界面把这个文件换成已校验的 NETCDF4_CLASSIC。
- Linux MPI 并行可执行文件这次没有在验证机上编出来，也没有做多节点试验。单机 OpenMP 的测定见上面的核数表。水动力在滇池这张小网格上增加线程往往没有收益；示踪物水平平流会随少数几个线程变快，然后进入平台期。
- 没有删除已有的计算结果。64 MB 的旧三维文件仍留在当时的运行目录里。
