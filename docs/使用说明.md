# 3DWET 使用说明

求解器是原生程序 `getm_cartesian`（Windows 上是 `3DWET/bin/getm_cartesian.exe`）。Python 只负责界面、启动和读结果，不另算一套水动力。

Windows：先运行 `setup_studio.cmd`，再双击 `launch_web.cmd`（浏览器）或 `launch_desktop.cmd`（桌面窗口）。仓库里的 `3DWET/bin/getm_cartesian.exe`（约 12 MB）已包含本次修复：Patankar 分母下限 `1e-12`，以及 `save_fabm_native`（默认关闭）。这是静态链接的串行程序，启动时用到的是 Windows 自带的 `KERNEL32`、`msvcrt`、`SHELL32`。`bin/runtime` 里的 DLL 仍保留，供界面检查安装是否完整。

Linux：在仓库里执行 `python3 3DWET/app/launcher.py --web --no-open`，浏览器打开它打印的地址。本机若还没有 Linux 可执行文件，用 `bash scripts/build_linux_solver.sh` 生成，不要把 `build-linux/`、`install-linux/` 或二进制提交进仓库。

## 跑滇池

案例在 `GETM-FABM-WET/3DWET/case/Lake Dianchi/`。网格是笛卡尔等距（`grid_type=1`，500 m，41×67，约 1150 个水格，10 层，步长 15 秒）。步长 60 秒会触到浅水河格的 CFL 限制，不能拿来和 EFDC 的 60 秒步长硬比。

求解只用笛卡尔、球面等距或正交曲线网格。界面里的三角网格选项、三角网按钮和“三角网”菜单都已去掉。食物网里的“三角闭环”指三条营养路径，仍然保留。

在「运行控制」里先做运行前体检，再开始。进度来自日志里的 `n=`。Patankar 在状态量接近 0 时会把分母托在 `1e-12`，重复警告只留前几条，避免进度停在某个百分比、日志被刷满。

## 运行监控

运行页上方的「运行监控」显示 MPI 进程数、OpenMP 线程数、步/秒、模拟天/墙钟小时、预计剩余时间、CPU，以及每个进程最近的输出。约 90 秒没有新步进，或日志里出现致命错误时，这一栏会高亮。

## 看结果

水位和深度平均流速在二维结果里。三维流速是 `uu`/`vv`。信息栏给出表层均值、底层均值和两者之差。原生三维文件里 `k=0`（sigma 最底的填充层）不是湖底，湖底是下一个有限层，水面是最后一层。

每天必写的关键量在 `output.nc`：水温、深度、层厚、水位、溶解氧。溶解氧的场名是 `abiotic_water_sO2W`（下划线）。叶绿素、氮磷、氨氮、硝氮、磷酸盐和有机碳氮磷按周放在 `ext_wq.nc`，点开变量才读，界面会缓存最近几帧。周文件在求解器初始化时创建。水质变量登记在类别 `fabm/<实例名>`，输出级别用 8。`output.yaml` 里要写 `fabm/abiotic_water/*`，不能写 `abiotic_water/*`。模拟不满 7 天时文件里还没有周记录。

原生 `*.3d.nc` 默认不再把全部 FABM 状态写进去（`save_fabm_native` 默认关闭，`getm.inp` 里不写这个开关）。同一天的滇池 WET 结果：旧文件约 64 MB、884 个变量；新文件约 756 KiB、24 个变量，仍有 `uu`，没有叶绿素。湿网格表层溶解氧均值约 9.61 g/m³（1150 个水格）。未掩膜的平均值会落到填充值附近，不要用。

## 速度（本机，2026-11-02，3 核）

同一台机器、滇池案例、模拟 1 天。墙钟是进程从启动到退出。

| 路径 | 墙钟 | 说明 |
| --- | --- | --- |
| `getm_cartesian`，关掉 FABM，1 个 OpenMP 线程 | 4.76 秒 | 步长 15 秒，5760 步，1150 个水格。模型计时合计 4.13 秒 |
| 同上，3 个线程 | 7.07 秒 | 这张小网格上 OpenMP 更慢。3 核机器默认就用 3 线程；核数不少于 4 时留给界面 1 个核 |
| 同上，打开 WET，1 个线程 | 101 秒 | 同一案例这次改前是 331 秒（更早一次测得 308 秒）。FABM/WET 从 326 秒降到 95 秒。水温、溶解氧、氨氮、蓝藻干重与改前逐点相同，最大差为 0 |
| Windows `getm_cartesian.exe`，Wine，WET，串行 | 146 秒 | 退出码 0。FABM/WET 135 秒。与 Linux 新程序这四个量逐点相同。旧程序 Wine 是 351 秒。三维文件仍是 773920 字节、24 个变量 |
| 开源 EFDC+（gfortran），温度，1 个线程 | 4.69 秒 | 工作副本：30×48，515 个水格，10 层，步长 60 秒，只开温度 |
| 同上，`-NT3` | 5.48 秒 | 程序报告 3 个线程。小网格上没有变快 |

水质时间大部分原来耗在搬运瞬时诊断量，不在水动力，也不在 Patankar 迭代本身。诊断场按水平网格存放，每个水柱都要大跨步拷贝一整列；采样时这一段约占积分时间的七成。这些量由当前状态重新计算，结果文件只在写入那一步读取。现在需要跨步累加的诊断量仍然每步保留，瞬时诊断量只在有文件要写、或打开了时间平均时写回整场。陆地格点原本就会跳过。`split_factor` 是把生物步再拆细，默认没有改。EFDC 那一行只有水动力和温度（`CWQ=0`），网格和步长也不同，所以完整 WET 仍然比它慢；水动力本身仍在 5 秒左右。

EFDC 源码和可执行文件留在本机 `/tmp`，仓库里没有 EFDC Explorer。另一台 12 线程电脑上的 `TIME.LOG`（约 3.5 秒）只作背景。

主路径用原生求解器。

## 还需要知道的限制

- Windows 程序在交叉编译时没有打开 OpenMP。MinGW 的 libgomp 会在 `clean_input` 退出阶段卡住，所以这个 exe 保持串行。界面可以设置 `OMP_NUM_THREADS`，本程序不使用它。
- 上述 Wine 1 天算例与 Linux 新程序写出同一大小的结果：`LAKE_DIANCHI_WET.3d.nc` 为 773920 字节、24 个变量（有 `uu`），`output.nc` 为 354420 字节，溶解氧场名 `abiotic_water_sO2W`，湿网格表层均值 9.6077 g/m³（1150 个水格）。
- `1e-12` 下限会在导数很小时把状态托住。旧算法一打印 Error 就被界面杀掉，所以没有一条“不改算法也能跑完”的对照。
- 每周 `ext_wq.nc` 的类别是 `fabm/<实例名>`，输出级别 8。旧的 `abiotic_water/*` 选不到这些变量，日志会写该类别没有匹配到请求的输出级别，文件不会创建。不满 7 天的运行可以有这个文件，但时间轴上还没有周记录。
- MPI 版 GETM 这次没有重编。这张网格上 OpenMP 已经测过，增加线程没有收益。
- 没有删除已有的计算结果。64 MB 的旧三维文件仍留在当时的运行目录里。
