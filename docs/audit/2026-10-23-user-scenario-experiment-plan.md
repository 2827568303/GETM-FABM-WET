# 用户场景与国际学术案例复现实验计划

负责人：GPT-6.1 Sol（高）；具体复现、实现和手册修改由 GPT-6 Luna（中）执行。

## 目的

以用户操作顺序验收：获取可追溯外部数据 → 导入并建立可运行案例 → 检查/构建/运行 → 动态查看 2D 与 3D 结果并旋转/缩放相机 → 配置一个真实鱼类或藻类竞争情景 → 成对运行并判断结果是否符合方程、输入和质量约束。用户手册需同步记录实际通过步骤、限制、来源与产物位置。

所有运行放在新的隔离目录内。失败的尝试保留原始日志并标为失败，不计作成功；重跑需记录新的尝试号。仅在 Sol 审核失败根因和修复方案后，由 Luna 实施代码修复。不得改写原始外部数据或生产案例来掩盖失败。

## 科学与软件验收门槛

1. 输入必须能追溯至原始 URL/数据门户及原始文件哈希；每个变量记录单位、时间、垂向含义和缺测转换。代理天气/空间几何与现场实测分开标记。
2. 对照和处理必须共享水动力/初值/强迫输入哈希。生态差异应是唯一、可解释的处理（如真实配置的竞争功能群或一个明确鱼类食性/初值变化），不能把复制同一实例伪称物种竞争。记录 FABM 实例与实际 prey/竞争耦合端口。
3. 原生输出必须覆盖预定时段且有多帧；检查湿网格有效值、单位、时间索引、负值/非有限值和关键质量收支。只有正常退出不算通过。
4. 用真实运行输出验收 2D/3D 播放：帧索引推进、颜色/范围随变量数据更新、播放时仍能旋转和缩放；相机状态在下一帧保留。静态截图、单元测试或单独官方 GOTM 结果不能替代该项。
5. 合理性判断先对照已发表论文的定性响应、方程和量纲，再报告本次指标。短时间步或代理几何仅能作为软件路径/数值 smoke test，不作为湖泊预测精度结论。
6. 每个发现先由 Sol 追踪到数据/算法/界面根因并写修复方案；Luna 才修改代码，添加回归和用户手册说明。代码修改后必须用隔离模型根启动服务或重启当前服务，并证明首页模板、静态资源哈希和页面版本均与源码一致。
