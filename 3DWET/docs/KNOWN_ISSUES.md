## 一、模型方程问题

### 1.1 草鱼模块完全缺失

**问题描述**：3DWET 模型完全缺失草鱼（Grass Carp）模块，而 PCLake+ 原版有完整实现。

**PCLake 草鱼模块规格**：
- 3 个状态变量：`sDGras`（草鱼干重）、`sPGras`（草鱼磷）、`sNGras`（草鱼氮）
- 16 个参数（3D 版本去掉 3 个无意义分层参数）
- 52 个方程（详见 `PCLake_WET_comparison_report.md` 和 `_pclake_dump/gras_only.md`）
- 19 个耦合点（需修改 4 个现有模块 + 新增 1 个模块）

**3 个草鱼专属机制（WET 无对应）**：

1. **仅食植被的 Holling III 型饱和摄食**：草鱼专食沉水植物，与其他鱼类食性不同。
2. **季节性 COS 捕捞切换**：草鱼有季节性捕捞压力（`cFishCrop` 参数），其他鱼类没有。
3. **植被低 P 触发的营养盐校正摄食**：当沉水植物 P 含量过低时，草鱼调整摄食策略。

**移植工作量**：
- 新建 `grass_carp.F90`（参考 `fish.F90` 结构）
- 修改 `macrophytes.F90`（增加草鱼牧食耦合）
- 修改 `om_pool.F90`（增加草鱼排泄产物）
- 修改 `abiotic_water.F90`（增加草鱼营养盐排泄）
- 修改 `CMakeLists.txt`（注册新模块）
- 预计工时：7 天

**影响**：缺少草鱼模块导致食物网不完整，无法模拟以沉水植物为主要食物源的鱼类生态过程，也无法表达草鱼对沉水植被的下行控制效应。

**原因**：WET 原版未移植 PCLake 的草鱼实现，3D 化过程中也未补齐。

**解决方案/建议**：按 PCLake 规格新建 `grass_carp.F90`，并在 4 个相关模块中实现 19 个耦合点；优先级见第七节 P2。

---

### 1.2 WET 鱼类模块双版本问题

**问题描述**：WET 有两个鱼类模块实现，功能重叠：

- **`fish_pclake.F90`（legacy 版）**：简单实现，与 PCLake 一致，无 foraging arena 概念。
- **`fish.F90`（标准版）**：含 foraging arena 机制，更复杂，当前 3DWET 使用此版本。

**影响**：
- 代码维护负担（两套实现需同步维护）。
- 用户选择困惑（不知该用哪个）。
- 参数命名可能不一致，跨模块对标易出错。

**原因**：历史遗留，legacy 版未在标准版上线后被清理。

**解决方案/建议**：整合为统一版本，废弃 `fish_pclake.F90`，保留 `fish.F90` 作为唯一鱼类实现。

---

### 1.3 浮游植物光照方程依赖

**方程**（`phytoplankton.F90:380-394`）：

```fortran
uLPARSurf = meanpar / EXP( -extc * dz/2.0_rk )
aLPARBot  = meanpar * EXP( -extc * dz/2.0_rk )
uOpt = uFunTm * self%cLOptRef
aLLim = exp(1.0_rk)/(extc*dz) * (exp(-aLPARBot/uOpt) - exp(-uLPARSurf/uOpt))
aMuTmL = ufDay * (1.0_rk - afCovSurfVeg) * aLLim * uFunTm * self%cMuMax
```

**问题**：`meanpar` 是 24h 平均 PAR（temporal_mean），依赖 `itime` 参数推进时间窗口。

- **修复前**：`getm_fabm.F90` 未传 `itime` → `meanpar=missing_value=0` → `aLLim=0` → 生长率=0。
- **修复后**：传递 `(yearday-1)*86400 + secondsofday` → `meanpar` 正常 → `aLLim=[0, 0.999]`。

**影响**：未传 `itime` 时浮游植物生长被完全抑制，整个食物网无法启动。

**原因**：宿主模型（GETM）与 FABM 的时间窗口接口未正确对接。

**解决方案/建议**：当前已修复 GETM 路径。**遗留风险**：如果其他宿主模型（非 GETM）使用 WET，需确保同样传递 `itime`；建议在 FABM driver 层增加 `itime` 缺失检测与告警。

## 二、参数问题

### 2.1 硅藻峰值过高

**现象**：异龙湖模拟中硅藻峰值达 44 gDW/m³（实际湖泊应 <10 gDW/m³）。

**可能原因**：
1. `cMuMax=2.4/d` 过高（PCLake+ 默认值，但 3D 环境中可能需降低）。
2. 损失率偏低（`cMort`、`cResp` 过低）。
3. 浮游动物牧食压力不足（虽然浮游动物稳定，但可能数量不够）。
4. 营养盐初始值过高（`NO3W=1.0 g/m³`）。

**影响**：硅藻异常爆发导致营养盐被快速消耗（见 2.2），破坏全年营养盐平衡与群落结构。

**原因**：3D 环境下物理输运与 PCLake 一维均质假设不同，默认参数未做适配。

**建议调整**：
- 降低 `cMuMax`：2.4 → 1.5–2.0
- 提高 `cMort`：当前值需核对 PCLake+ Excel
- 降低初始 `NO3W`：1.0 → 0.5–0.7

---

### 2.2 营养盐年末耗尽

**现象**：`NH4W`/`NO3W`/`PO4W` 年末全部耗尽至 0。

**原因**：硅藻过度消耗（与 2.1 相关）+ 河流输入营养盐浓度偏低。

**影响**：年末初级生产力因营养盐限制而崩溃，影响次年春季群落重建，与实际观测不符。

**建议**：
- 提高河流输入营养盐浓度（INFL2 的 `nh4` 从 0.30 提高到 0.5）
- 或降低硅藻 `cMuMax` 减少消耗
- 或增加沉积物营养盐释放（`kNitrS`、`kPSorpS` 调整）

---

### 2.3 绿藻净生长率过低

**现象**：绿藻在异龙湖模拟中虽然稳定（max=0.23），但增长缓慢。

**参数对比**：

| 参数 | 蓝藻 | 硅藻 | 绿藻 |
|------|------|------|------|
| `cMuMax` | 1.5 | 2.4 | **1.0** ←最低 |
| 净生长率 | 1.37 | 2.30 | **0.925** ←最低 |
| 最适温度 | 25°C | 18°C | 25°C |
| 沉降速率 | +0.03(上浮) | -0.50(下沉) | -0.35(下沉) |

**问题**：绿藻 `cMuMax=1.0` 可能是 PCLake+ 默认值，但在 3D 环境中净生长率 0.925 过低，容易被竞争排除。

**影响**：绿藻在群落中占比偏低，无法再现实际湖泊中绿藻作为春季/初夏优势类群的现象。

**原因**：参数未针对 3D 环境重新标定。

**建议**：核对 PCLake+ Excel `PL613162PLUS.xls` 中 greens 的 `cMuMax`，可能应为 1.5–2.0。

---

### 2.4 PCLake+ 参数全面对标需求

**现状**：3DWET 只调整了关键参数，621 个 PCLake+ 参数需逐一核对。

**待核对参数类别**：
- 浮游植物参数（3 群 × 30+ 参数）
- 浮游动物参数（2 群 × 20+ 参数）
- 鱼类参数（3 功能群 × 25+ 参数）
- 沉水植物参数（20+ 参数）
- 底栖动物参数（15+ 参数）
- 营养盐循环参数（40+ 参数）
- 有机质参数（20+ 参数）

**参考文件**：`PL613162PLUS.xls`（551 参数，135 状态变量，24 工作表）

**影响**：未对标的参数可能在 3D 环境下产生偏差，累积影响模型可信度。

**解决方案/建议**：建立参数对标脚本/对照表，分批核对（每批 1 类生物群），优先级见第七节 P2。

## 三、工程问题

### 3.1 Patankar 警告日志膨胀

**问题描述**：`ode_method=10`（Patankar 保正）产生大量 "Warning: small pi=0" 警告。

- 每步约 35 条警告
- 366 天累计数千万条
- `run.log` 易超 100MB，被系统终止

**影响**：日志体积失控导致运行被系统杀死，且有用诊断信息被淹没。

**原因**：Patankar 求解器在 `pi` 接近 0 时未对告警做级别分级或限频。

**当前解决**：运行时 grep 过滤

```bash
getm_cartesian 2>&1 | grep -v 'small pi' > run.log
```

**根本解决建议**：
- 修改 WET 源码，将 "small pi" 警告降级为 DEBUG 级别
- 或在 `gotm_fabm.yaml` 增加 `log_level` 配置

---

### 3.2 NetCDF3 numrecs=0 问题

**问题描述**：GETM 因 meteo EOF 异常退出时，NetCDF3 输出文件 `numrecs=0`（头部未更新）。

**症状**：
- 文件大小正常（数据已写入）
- 但 NetCDF 库无法读取（显示 0 条记录）
- Python netCDF4 读取报 `IndexError`

**影响**：异常退出后输出文件不可读，需手工修复才能恢复数据。

**原因**：NetCDF3 经典格式的 record count 字段在异常退出时未 flush。

**当前解决**：`patch_numrecs.py` 修复 4 字节 `numrecs` 字段

```python
# 修复 NetCDF3 头部 offset 4 的 numrecs 字段
import struct
with open(filepath, 'r+b') as f:
    f.seek(4)
    f.write(struct.pack('>I', num_recs))
```

**根本解决建议**：
- GETM 退出前强制 flush NetCDF3 文件
- 或改用 NetCDF4 格式（支持 unlimited dimension）

### 3.4 沉水植物扩散过快

**问题描述**：沉水植物 14 天后从初始 8% 湖面积（96 网格）扩散到全湖（1198 网格）。

**影响**：
- 与实际不符（沉水植物应限制在湖滨带）
- 影响光照分布（过度遮光）
- 影响沉积物再悬浮（过度保护）

**原因**：扩散参数未在 3D 环境下标定，扩散速率过大。

**当前解决**：通过 `fabm_init.nc` 仅设置浅水区初始分布。

**根本解决建议**：调整 macrophytes 扩散参数（需核对 PCLake+ 默认值）。

---

### 3.5 鱼类状态变量单位混淆

**问题描述**：鱼类状态变量单位是体积基础（gDW/m³），但底栖动物/沉水植物是面积基础（gDW/m²）。

**影响**：
- 3D 中鱼类变量与底栖变量耦合时需转换。
- `bot_pel_conv`（底栖-浮游转换因子）的正确应用易出错。

**原因**：WET 模块沿用各自传统单位制，未统一。

**当前状态**：已通过 `bot_pel_conv` 处理，但概念上易混淆。

**解决方案/建议**：在文档中明确标注各模块单位制；长期考虑在状态变量元数据中强制声明 units 并自动校验。

## 四、模型结构问题

### 4.1 bot_pel_conv 横向链接风险

**问题描述**：`bot_pel_conv` 曾因 `link_bulk_data` 使用不当导致段错误。

**正确方法**：

```fortran
allocate(bot_pel_conv_col(kmax))
bot_pel_conv_col = _ONE_
call model%link_bulk_data(type_bulk_standard_variable(name='bot_pel_conv',units='-'), &
                         bot_pel_conv_col(1:kmax))
```

**影响**：错误链接会导致运行时段错误，难以定位。

**原因**：FABM 接口的 bulk vs horizontal 数据语义混淆。

**注意事项**：**不要用 `link_horizontal_data` 链接 `bot_pel_conv`**。

**解决方案/建议**：在模块开发规约中固化此写法，并在代码审查 checklist 中加入该项检查。

---

### 4.2 hypsograph 禁用要求

**问题描述**：`abiotic_sediment` 和 `bot_pel_interface` 的 `hypsograph` 必须禁用。

**原因**：3D 模式下沉积物是逐格处理的，不需要 hypsograph（湖面积-深度关系）。

**影响**：若启用会导致沉积物通量被错误聚合/分配，破坏空间一致性。

**配置**：

```yaml
abiotic_sediment:
  parameters:
    hypsograph: false
bot_pel_interface:
  parameters:
    hypsograph: false
```

**解决方案/建议**：在 `fabm.yaml` 模板中默认置 `false` 并加注释说明；启动前校验配置。

---

### 4.3 resus_sed 模块状态

**问题描述**：较新版本 WET 使用 `om_pool` 模块，已移除 `resus_sed` 模块。

**现状**：3DWET 使用 `om_pool`（正确），但部分旧配置可能引用 `resus_sed`。

**影响**：旧配置在新版 WET 上启动失败或行为不一致。

**建议**：确保所有 case 的 `fabm.yaml` 使用 `om_pool` 而非 `resus_sed`；提供配置迁移检查脚本。

---

### 4.4 时间步 30 秒硬约束

**问题描述**：时间步必须 30 秒，否则数值不稳定（河流入流附近高流速导致 CFL 违约）。

**影响**：
- 366 天模拟需 1,051,200 步
- 28×8 网格约 90 分钟（8 线程）
- 计算量大

**原因**：河流入流局部流速高，固定时间步无法兼顾全局效率与局部稳定。

**替代方案**（未验证）：
- 采用自适应时间步
- 或河流入流附近局部细化网格

## 五、数据准备问题

### 5.1 gen_bathymetry.py polyfit Bug（已修复）

**问题描述**：`latc` 用 `np.polyfit(old_y, old_latc.ravel()[:len(old_y)], 1)` 拟合。

- `ravel()[:len(old_y)]` 取了 `(ny, nx)` 数组的前 54 个元素（第 0 行 44 个 + 第 1 行 10 个）
- 但 `latc` 主要沿 y 变化（不沿 x）
- 拟合 slope ~60x 太小

**影响**：生成的纬度坐标严重错误，导致 bathymetry 空间定位失效。

**原因**：对 2D 数组做 `ravel()` 后取前 N 个元素，误把行优先展开当作列向量。

**修复**：用直接 UTM→lat/lon 转换替代 polyfit（`gen_bathymetry.py` 的 `utm_to_latlon` 函数）。

---

### 5.2 meteo.nc 维度顺序陷阱

**问题描述**：Fortran netCDF 4.5.4 库会反转维度顺序（C order → Fortran column-major）。

**表现**：
- C 变量维度 `(lon, lat, time)` → Fortran 读取为 `(time, lat, lon)` → `NC_EEDGE` 错误(-57)
- C 变量维度 `(time, lat, lon)` → Fortran 读取为 `(lon, lat, time)` → 正确

**影响**：meteo 数据维度顺序错误会导致读取失败或数据错位，驱动模型异常退出。

**原因**：C/Fortran 内存布局差异 + netCDF 接口行为。

**规则**：**meteo.nc 的 C 变量维度必须为 `(time, lat, lon)`**。建议在 `gen_meteo.py` 中强制该校验。

---

### 5.3 riverinfo.dat 索引顺序

**问题描述**：`riverinfo.dat` 用 1-based 索引，`i=列(x方向)`，`j=行(y方向)`，易混淆。

**示例**：DAYUN 必须在 `i=2, j=32`（西湖边），不是 `i=7, j=32`（湖中心）。

**影响**：索引方向理解错误会导致河流入流点位置错误，水量/营养盐输运完全偏离。

**规则**：
- 1-based 索引（不是 0-based）
- `i=列`（x 方向，从左到右 1,2,3...）
- `j=行`（y 方向，从上到下 1,2,3...）

**解决方案/建议**：在 `riverinfo.dat` 文件头部以注释固化规则；提供可视化校验脚本（已有 `check_river_positions.py`）。

## 六、验证与测试问题

### 6.1 缺乏质量平衡诊断

**问题描述**：无系统性的质量平衡诊断脚本。

**需求**：
- 营养盐平衡（输入 - 输出 - 沉积 - 生物吸收）
- 碳平衡（初级生产力 - 呼吸 - 埋藏）
- 水量平衡（已有，水位净变化）

**影响**：无法定量评估模型闭合性，难以发现隐藏的通量泄漏或单位错误。

**建议**：开发 `mass_balance` 诊断脚本（预计 2 天），优先级见第七节 P2。

---

### 6.2 缺乏多湖泊交叉验证

**问题描述**：仅在骆马湖、理论湖、异龙湖测试，缺乏其他湖泊验证。

**影响**：模型通用性未充分验证，参数可移植性存疑。

**建议**：
- 增加浅水富营养化湖泊（如太湖局部）
- 增加深水湖泊（如抚仙湖）
- 与 QWET 1D 结果对比

---

### 6.3 3D 温度曾误报 NaN

**问题描述**：理论湖泊测试中 3D 温度一度误报为全 NaN。

**根因**：`numrecs=0` 时 NetCDF3 的 time 维度为空，无法读取。

**影响**：误判为模型数值崩溃，浪费排查时间。

**修复**：`patch_numrecs.py` 先修复再读取。

**注意**：这是数据读取问题，非模型问题。建议在读取流程中默认执行 numrecs 校验。
