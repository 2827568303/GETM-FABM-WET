## 一、项目概述

### 1.1 项目目标

3DWET 项目旨在开发一个**三维水动力-水质-食物网耦合模型**，用于湖泊生态系统的模拟、预测和管理支持。模型的核心目标包括：

- **完整的三维水动力模拟**：水流场、温度场、物质输运全过程
- **完整的水质模块**：营养盐（N/P/Si）循环、溶解氧平衡、有机质降解
- **完整的食物网结构**：
  - 浮游植物 3 群（硅藻、绿藻、蓝藻）
  - 浮游动物 2 群（枝角类、桡足类）
  - 沉水植物
  - 底栖动物
  - 鱼类 3 功能群（幼鱼、底栖食性鱼、浮游食性鱼）
- **面向中国湖泊场景**：骆马湖、异龙湖等浅水湖泊的生态环境管理
- **支持 GUI 界面**：降低科研院所和工程单位的使用门槛

### 1.2 技术路线

模型基于 GETM-FABM-WET/PCLake 耦合架构构建，采用国际成熟的开源生态建模框架：

```
3DWET 技术栈
┌──────────────────────────────────────────────────────────┐
│  WET  (Water Ecology Treatment)                          │
│  瓦赫宁根大学开发，PCLake 的 FABM 版本                   │
│  职责：水质、浮游生物、沉水植物、底栖、鱼类、食物网      │
└────────────────────────▲─────────────────────────────────┘
                         │ FABM 耦合接口
┌────────────────────────┴─────────────────────────────────┐
│  FABM (Framework for Aquatic Biogeochemical Models)      │
│  生地化耦合框架，Bolding & Bruggeman 开发                 │
│  职责：模型耦合、状态变量管理、垂直分布、时间积分        │
└────────────────────────▲─────────────────────────────────┘
                         │ 湍流闭合
┌────────────────────────┴─────────────────────────────────┐
│  GOTM (General Ocean Turbulence Model)                   │
│  通用海洋湍流模型                                        │
│  职责：垂直湍流、混合层、k-ε 模型                        │
└────────────────────────▲─────────────────────────────────┘
                         │ 水动力驱动
┌────────────────────────┴─────────────────────────────────┐
│  GETM (General Estuarine Transport Model)                │
│  通用河口输运模型                                        │
│  职责：3D 水流、温盐、平流扩散、地形处理                 │
└──────────────────────────────────────────────────────────┘
```

**技术选型理由**：

- **GETM**：成熟的三维浅水水动力模型，支持曲线坐标、干湿边界，适合湖泊
- **GOTM**：国际主流的湍流闭合模型，与 GETM 无缝集成
- **FABM**：模块化生地化框架，支持多模型耦合，避免重复开发
- **WET**：基于 PCLake 的全生态系统模型，已包含 104 个状态变量，覆盖完整食物网

### 2.2 关键技术突破

#### 2.2.1 浮游植物光照耦合修复（P0 修复）

**问题描述**：浮游植物生物量持续为 0，整个生态系统无法启动。

**根因定位**：
```
getm_fabm.F90 未传递 itime
    ↓
FABM 中 meanpar 计算 = 0
    ↓
WET 浮游植物 aLLim（光照限制因子）= 0
    ↓
浮游植物生长率 = 0
    ↓
整个食物网无能量来源，崩溃
```

**修复方案**：
在 `getm_fabm.F90` 中正确传递时间参数：
```fortran
! 传递年内秒数，确保 24h 平均 PAR 计算正确
itime = (yearday - 1) * 86400 + secondsofday
```

**修复效果**：
- aLLim 从恒 0 变为 [0, 0.999] 的合理范围
- 浮游植物开始正常生长
- 食物网能量传递链恢复正常

#### 2.2.2 生态级联崩溃修复（P1 配置修复）

**问题描述**：异龙湖案例运行过程中出现生态级联崩溃——浮游动物先饿死，鱼类随后崩溃，硅藻最终暴发。

**根因分析**：
```
初始浮游植物过低 (0.05)
    ↓
浮游动物食物不足，能量收支为负
    ↓
浮游动物种群崩溃
    ↓
鱼类失去食物来源，幼鱼先崩溃，成鱼后崩溃
    ↓
浮游动物捕食压力消失，硅藻失去控制性竞争
    ↓
硅藻暴发（峰值 44 gDW/m³）
```

**修复方案**（调整初始条件）：
| 参数 | 修复前 | 修复后 | 说明 |
|------|--------|--------|------|
| 浮游植物初始 | 0.05 | 0.2-0.3 | 提高食物基础 |
| 浮游动物初始 | 0.10 | 0.30 | 配合浮游植物提升 |
| 鱼类初始 | 基准值 | 降低 50% | 降低捕食压力 |

**修复效果**：
- 浮游动物全年稳定（0.24 → 0.25）
- 鱼类全年稳定（幼鱼 0.15 → 0.16）
- 蓝藻秋季水华（峰值 6.84）符合浅水湖泊典型特征

#### 2.2.3 数值稳定性保障

为保证 366 天长期模拟的数值稳定，采用以下关键配置：

1. **ode_method = 10**（Patankar 方法）
   - 保正性：保证状态变量始终非负
   - 与 QWET 1D 基准模型一致，便于对比验证
   - 副作用：产生 "small pi=0" 警告（见 4.3）

2. **repair_state = true**
   - 主动修复负值（数值误差引起）
   - 避免负值传播导致方程无意义

3. **shade = true**
   - 启用生物自遮光反馈
   - 藻类浓度过高时自遮光，抑制生长
   - 对藻类峰值有重要调节作用

4. **时间步长 30 秒**
   - 兼顾稳定性与计算效率
   - 8 线程下 366 天模拟约 22 分钟

#### 2.2.4 水平衡精确控制

湖泊模型水平衡是基础性指标，本项目通过以下措施实现 366 天净变化 0.0000 m：

1. **数据精度：float64**
   - 降水/蒸发数据使用 float64 而非 float32
   - 避免浮点精度丢失引起的累积误差

2. **fwf_method = 2**
   - 从文件读取淡水通量，而非内部计算
   - 保证输入端精度可控

3. **严格平衡约束**
   ```
   出流 = 入流 + 降水 - 蒸发
   ```
   - 通过出流动态调节实现严格平衡
   - 366 天净水位变化 0.0000 m

## 四、现存问题

### 4.1 模型方程问题

#### 4.1.1 草鱼模块完全缺失

**问题**：3DWET 当前无草鱼模块，而 PCLake 原版有完整实现。

**PCLake 草鱼模块规模**：
- 3 个状态变量：sDGras / sPGras / sNGras（鱼体干重、磷、氮）
- 16 个参数
- 52 个方程
- 19 个耦合点（与沉水植物、有机质、营养盐等模块交互）

**影响**：草鱼是中国浅水湖泊的关键生态管理对象（如骆马湖、东太湖），缺失草鱼模块将限制模型在沉水植物管理场景下的应用。

#### 4.1.2 3 个草鱼专属机制无对应

PCLake 草鱼模块包含 3 个 3DWET 中完全没有的机制：

1. **Holling III 型饱和摄食**：仅食植被，与沉水植物耦合
2. **季节性 COS 捕捞切换**：模拟中国湖泊的草鱼轮捕轮放管理
3. **植被低 P 触发的营养盐校正摄食**：草鱼通过摄食调节沉水植物 C:N:P 比

#### 4.1.3 WET 鱼类模块冗余

WET 中存在两个鱼类模块：
- `fish_pclake.F90`：legacy 简单版，无 foraging arena 机制
- `fish.F90`：标准版，含 foraging arena（觅食场所）理论

**当前选择**：使用 `fish.F90`（标准版），保留 `fish_pclake.F90` 作为参考。

**建议**：中期整合为统一版本，避免维护混乱。

### 4.2 参数问题

#### 4.2.1 硅藻峰值过高

- **现象**：硅藻峰值达 44 gDW/m³，实际湖泊应 <10 gDW/m³
- **可能原因**：
  - `cMuMax`（最大生长率）过高
  - 损失率（呼吸、沉降、捕食）过低
  - 营养盐供给过盛
- **解决方向**：调参试验，建议优先降低 cMuMax

#### 4.2.2 营养盐年末耗尽

- **现象**：年末营养盐浓度接近 0，硅藻过度消耗
- **解决方向**：
  - 提高河流输入营养盐浓度
  - 或降低硅藻参数（与 4.2.1 联动）

#### 4.2.3 绿藻净生长率最低

| 浮游植物群 | 净生长率 | 评价 |
|------------|----------|------|
| 硅藻 | 2.3 | 最高 |
| 蓝藻 | 1.37 | 中等 |
| 绿藻 | 0.925 | 最低 |

**问题**：在均匀环境下，净生长率最低的绿藻会被竞争排除。需检查 `cMuMax=1.0` 是否合理（PCLake 默认可能更高）。

#### 4.2.4 PCLake+ 参数对标未完成

- PCLake+ Excel 默认值共 621 个参数
- 当前仅调整了关键参数（cMuMax、初始条件、损失率等）
- 长期需逐一核对，确保参数生态学合理

### 4.3 工程问题

#### 4.3.1 Patankar 警告日志膨胀

- **现象**：`ode_method=10` 产生大量 "small pi=0" 警告
- **影响**：`run.log` 易超 100 MB，影响日志查阅
- **临时方案**：运行时用 `grep -v "small pi"` 过滤
- **根本方案**：评估 ode_method 选择，或修改 WET 中 Patankar 警告阈值

#### 4.3.2 NetCDF3 numrecs=0 问题

- **现象**：GETM 异常退出（如 meteo EOF 提前结束）时，NetCDF3 头部 `numrecs` 字段不更新
- **影响**：输出文件看似存在但记录数为 0，可视化脚本读取失败
- **临时方案**：使用 `patch_numrecs.py` 修复历史输出文件
- **预防**：保证输入数据完整，运行前检查 meteo.nc 时间序列

#### 4.3.3 无 GUI 界面

- **现状**：仅命令行运行
- **影响**：不满足科研院所/工程单位的 GUI 需求
- **计划**：长期开发 Python tkinter/PyQt 封装

#### 4.3.4 无云服务

- **现状**：按要求本地运行
- **影响**：数据不出本地，符合数据安全要求
- **评价**：当前设计满足需求，无需额外改造

### 4.4 模型结构问题

#### 4.4.1 沉水植物扩散过快

- **现象**：14 天后沉水植物从初始 8% 湖面积扩散到全湖
- **影响**：无法体现湖滨带 vs 湖心区的空间差异
- **解决方向**：调整扩散系数，或限制沉水植物仅在浅水区生长

#### 4.4.2 鱼类状态变量单位混淆

- **问题**：鱼类状态变量单位在体积（gDW/m³）与面积（gDW/m²）之间存在转换混淆
- **影响**：3D 模型中深度变化时单位转换易错
- **建议**：明确统一约定，并在代码中添加单位注释

#### 4.4.3 bot_pel_conv 横向链接

- **历史**：曾导致段错误
- **现状**：已修复
- **注意**：后续修改底栖-水柱耦合代码时需重点关注

## 五、经验教训

### 5.1 数据准备

#### 5.1.1 精度至关重要

float32 vs float64 的差异可能导致水平衡失效。本项目曾因降水/蒸发数据使用 float32 导致 366 天累积误差显著，改用 float64 后实现 0.0000 m 净变化。

**教训**：水文量（降水、蒸发、流量）必须使用 float64，避免长期累积误差。

#### 5.1.2 索引顺序易错

- GETM 使用 1-based 索引，`i` 为列、`j` 为行
- Python 使用 0-based 索引
- 不一致会导致数据错位

**教训**：数据生成脚本中需明确索引约定，并在注释中标注。

#### 5.1.3 维度顺序

Fortran 写入 NetCDF 会反转 C order。meteo.nc 必须以 `(time, lat, lon)` 顺序写入，否则 GETM 读取会出错。

**教训**：跨语言（Python→Fortran）数据交换时，需特别检查维度顺序。

#### 5.1.4 单位一致性

本项目统一约定：
- 流量单位：m³/s
- 浓度单位：g/m³
- 时间单位：秒（s）
- 长度单位：米（m）

**教训**：单位不一致是隐蔽且致命的 bug 源，必须在数据准备阶段就统一。

### 5.2 模型调试

#### 5.2.1 从简单到复杂

本项目采用三层测试体系：
```
2D shell 测试（仅水动力）
    ↓
3D + GOTM 测试（水动力 + 湍流）
    ↓
FABM-WET 完整测试（水动力 + 湍流 + 生态）
```

**教训**：分层测试能快速定位问题层次，避免在完整系统中调试难以定位的 bug。

#### 5.2.2 先稳定再生态

调试顺序：
1. 先确保水动力稳定（水位平衡、流量守恒）
2. 再确保热力合理（温度季节变化）
3. 最后加入生态模块（营养盐、浮游生物、鱼类）

**教训**：水动力是基础，基础不稳则生态结果无意义。

#### 5.2.3 基准对比

QWET 1D 模型是本项目的重要基准：
- ode_method 应与 QWET 一致（=10）
- 关键参数对照 QWET 默认值
- 1D vs 3D 结果可对比验证

**教训**：选择合适的基准模型对比，能快速发现实现错误。

#### 5.2.4 光照耦合是关键

WET 浮游植物依赖 24h 平均 PAR，时间参数必须正确传递。本项目 P0 级 bug 即因 `itime` 未传递导致 aLLim=0，整个生态系统崩溃。

**教训**：FABM 框架与外部驱动模型耦合时，时间参数传递是常见且致命的 bug 源。

### 5.3 生态建模

#### 5.3.1 初始条件敏感

异龙湖案例的级联崩溃证明：浮游植物初始过低 → 浮游动物饿死 → 鱼类崩溃 → 硅藻暴发，是典型的级联反馈。

**教训**：生态系统模型对初始条件敏感，需要合理的初始值避免级联崩溃。

#### 5.3.2 竞争排除

在均匀环境下，净生长率最低的物种会被竞争排除。本项目绿藻净生长率最低（0.925），在均匀环境下易被排除。

**教训**：多物种竞争模型中，需保证各物种生态位差异化，避免均匀环境下竞争排除。

#### 5.3.3 PCLake 双态

PCLake 默认参数分 Turbid（浑浊）和 Clear（清水）两种状态，参数差异较大。

**教训**：需根据湖泊实际状态选择合适的默认参数集。

#### 5.3.4 生物自遮光

`shade=true` 启用生物自遮光反馈，对藻类生长有重要调节作用。

**教训**：生物反馈机制对生态系统稳定性至关重要，不应轻易关闭。

### 5.4 工程实践

#### 5.4.1 Patch 管理

所有 Bug 修复均以 patch 文件形式管理：
- 保留上游源码原貌
- 修改可追溯
- `build_model.sh` 自动应用

**教训**：第三方代码修改用 patch 管理，便于上游升级合并。

#### 5.4.2 日志过滤

Patankar 警告需 grep 过滤，避免日志膨胀。

**教训**：数值方法产生的诊断警告需配套日志过滤策略。

#### 5.4.3 numrecs 修复

NetCDF3 异常退出需 `patch_numrecs.py` 修复。

**教训**：异常退出场景下的输出文件修复工具是必要的工程保障。

#### 5.4.4 多线程

配置：
```
OMP_NUM_THREADS=8
OMP_SCHEDULE=dynamic
```

效果：相比单线程加速约 5 倍。

**教训**：合理配置 OpenMP 线程数和调度策略，对计算效率影响显著。
